# 为什么我不做搜索网站，只做 SDK

> 市面上"xxx 搜索"网站越来越多，但合规痛点也越来越明显：DMCA 投诉、平台 ToS 限制、数据爬取法律风险。我选择了一条反向的路：不做网站，只发 npm 包，规则在用户本机跑。本文聊聊这个决策背后的思考。

## 市面上"搜索聚合"网站的合规痛点

如果你搜过"聚合搜索""资源搜索""学术搜索"这类词，一定见过不少"xxx 聚合搜索"网站。它们的模式大同小异：

1. 服务端爬取多个数据源
2. 用户在网站搜索框输入关键词
3. 服务端查询 + 返回结果
4. 结果展示在网页上

这个模式的问题：

**DMCA 投诉风险**：如果数据源包含版权内容，权利人可以发 DMCA 投诉要求下架。网站作为中间方，承担内容责任。

**平台 ToS 限制**：很多数据源的 ToS 明确禁止自动化爬取。网站大规模爬取可能违反 ToS，面临封 IP / 法律追究。

**数据爬取法律风险**：不同司法辖区对数据爬取的法律界定不同（如美国 hiQ vs LinkedIn 案、国内反不正当竞争法）。网站作为爬取主体，法律风险集中。

**搜索词隐私**：用户的搜索词经过网站服务器，网站知道你搜了什么。如果搜索词涉及敏感内容，隐私风险。

**内容审核责任**：网站展示结果，可能被要求承担内容审核责任。如果结果里有违规内容，网站要负责。

这些痛点本质上是同一个问题：**网站作为中间方，承担了内容责任**。

## SeekAll 的反向决策：不做网站，只做 SDK

我选择了一条反向的路：

**不做网站，只发 npm 包。**

SeekAll 的核心是一个规则引擎 SDK（`@seekall/sdk`），加上一个规则市场（npm 包分发）+ BaaS（账号 / 规则列表 / DMCA 邮箱）。

工作方式：

1. 用户 `npm i @seekall/sdk` 装到本机
2. 用户自己写规则或从规则市场装规则（也是 npm 包）
3. 用户在本机跑 `engine.search('keyword')`
4. 规则在本机发出 HTTP 请求到数据源
5. 结果返回给用户本机

**关键区别**：SeekAll 的服务端**不参与搜索**。

- 服务端不爬任何数据源
- 服务端不接收用户的搜索词
- 服务端不返回任何搜索结果
- 服务端只做：账号管理、规则市场列表、DMCA 邮箱接收

这意味着：

- 搜索词只经过用户本机 + 数据源，不过 SeekAll 服务器
- 数据源请求是用户本机发出的（用户自己承担合规责任，和用浏览器访问一样）
- SeekAll 作为平台，零接触资源内容

## 5 级风险评级：工具中性的设计哲学

但"工具中性"还不够。数据源本身有风险等级差异：arxiv 是学术纯净的，但有些资源站是灰色地带的。如果 SeekAll 默认提供所有规则，等于变相引导用户访问高风险源。

所以我设计了 **5 级风险评级**：

| 级别 | 说明     | 可见性                  | 示例                                |
| ---- | -------- | ----------------------- | ----------------------------------- |
| L0   | 学术纯净 | 公开，免费              | arxiv, crossref, pubmed             |
| L1   | 通用开源 | 公开，免费              | GitHub, Hacker News, Stack Overflow |
| L2   | 社区评审 | 公开（需评审通过）      | 特定社区 API                        |
| L3   | 高风险   | 仅 admin 可见           | 灰色地带资源站                      |
| L4   | 极高风险 | 仅 admin 可见，永不公开 | -                                   |

**核心规则**：

1. L0-L2 规则在规则市场公开，任何人可以装
2. L3-L4 规则**永远不对非 admin 可见**，即使付费也不行
3. 服务端代码（`apps/api/src/modules/rule/`）里**没有 `axios`/`fetch`/`http`**，服务端不调任何资源站
4. 不做评论 / 评分 / 论坛功能（避免 UGC 内容责任）

这样设计后，SeekAll 作为一个平台：

- **不接触资源内容**：服务端只存规则元数据（name、npm 包名、风险评级、描述），不存搜索结果
- **不引导高风险访问**：L3-L4 规则不公开，普通用户看不到
- **不承担 UGC 责任**：没有评论 / 论坛，没有用户生成内容

工具是中性的，但数据源不是。SeekAll 选择做"引擎"而不是做"资源站"--我们提供能力，你来决定搜什么。L0-L2 你自己装，L3-L4 你看不到。

## 工具中性 vs 平台责任的边界

这个设计引出一个值得讨论的问题：**工具中性 vs 平台责任的边界在哪？**

以 BitTorrent 为例：BitTorrent 协议本身是中性的（可以分发 Linux ISO，也可以分发版权内容）。但 BT 索引站因为索引 + 提供资源定位，承担了版权责任。

SeekAll 的选择：

- **做协议 / 引擎**（像 BitTorrent 协议）：SDK 是中性的，规则在用户本机跑
- **做规则市场**（不像 BT 站点）：规则市场只索引 npm 包（L0-L2），不索引资源内容
- **不做资源索引**：SeekAll 不索引任何资源站的内容，只索引"规则"（规则的代码在 npm 上）

这个边界的关键是：**SeekAll 知道"有哪些规则"，但不知道"规则能搜到什么"**。规则能搜到什么，只有用户本机跑了才知道。

这跟 BT 索引站的区别是：BT 索引站索引的是"资源"（资源定位指向具体内容），SeekAll 索引的是"工具"（规则代码指向 API 端点，不指向具体内容）。

## 这个设计的代价

工具中性是有代价的：

**用户体验**：用户要 `npm i` 装包 + 写代码，不如网页搜索方便。SeekAll 面向的是开发者 / 研究人员，不是普通用户。

**冷启动难**：默认 0 规则，用户装了 SDK 不知道搜什么。需要靠规则市场 + 社区贡献。但"默认 0 规则"是合规设计的必要条件，不是 bug。

**商业模式限制**：不能靠"资源变现"（如广告、付费解锁资源），只能靠"性能变现"（免费 3 并发 vs 付费 10 并发 + 缓存）。天花板较低。

**技术门槛**：规则要写代码（虽然 10 行就够），不如网页搜索零门槛。但这也过滤掉了一部分滥用。

这些代价是深思熟虑后的选择。工具中性的路更难走，但更稳。

## 总结

SeekAll 的设计哲学：

1. **不做网站，只做 SDK**：搜索在本机跑，服务端零接触
2. **5 级风险评级**：L0-L2 公开，L3-L4 永不公开
3. **服务端不调资源站**：代码里没有 `axios`/`fetch`/`http`
4. **不做 UGC**：没有评论 / 评分 / 论坛
5. **规则市场只索引工具，不索引资源**：和 BT 站点划清边界

这不是最赚钱的路，但是最稳的路。工具中性不是逃避责任，而是划清责任边界--SeekAll 提供引擎，你来决定搜什么，各自的合规责任各自承担。
