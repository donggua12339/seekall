## 一、审计结论

**总体评价**：项目架构合理，业务逻辑完整，但存在多处影响运行稳定性和安全性的细节问题。本次审计发现 **12 个问题**，已全部修复。问题主要集中在：

## 二、已修复问题清单

### 严重（影响功能）

#### 1. start-dev.bat 路径空格导致后端启动失败
- **现象**：`api.err.log` 报 `Cannot find module 'D:\soft\Claude'`
- **根因**：项目路径 `D:\soft\Claude Code Haha` 含空格，`cmd /c "node dist\main.js"` 在某些情况下路径被空格截断
- **修复**：改用 PowerShell `Start-Process` + `-WorkingDirectory`，可靠处理含空格路径
- **文件**：`start-dev.bat`、`stop-dev.bat`

#### 2. profile.vue savePreferences 引用未定义字段
- **现象**：保存偏好设置时发送 `language`、`preferredCategories`、`preferredProviders` 字段，但 reactive 对象只定义了 3 个字段
- **根因**：前端 reactive 对象与后端 DTO 字段不一致
- **修复**：补全 reactive 对象字段，与后端 `PreferencesDto` 对齐
- **文件**：`apps/web/pages/profile.vue`

#### 3. layouts/default.vue 用了不存在的 NuxtLoadingProvider 组件
- **现象**：nuxt.out.log 持续刷 `Failed to resolve component: NuxtLoadingProvider`
- **根因**：Nuxt 没有名为 `NuxtLoadingProvider` 的组件（应为 `NuxtLoadingIndicator`，但本场景不需要）
- **修复**：移除外层 `<NuxtLoadingProvider>` 包裹
- **文件**：`apps/web/layouts/default.vue`

#### 4. link_status.url 列长度不足
- **现象**：搜索时后端日志刷 `The provided value for the column is too long for the column's type. Column: url`
- **根因**：Prisma schema 中 `url` 为 VarChar(512)，但部分夸克/百度网盘分享 URL 超过 512 字符
- **修复**：改为 VarChar(2048)，`prisma db push` 同步
- **文件**：`apps/api/prisma/schema.prisma`

### 中等（影响体验/安全）

#### 5. .env 端口配置遗留错误
- **现象**：GitHub OAuth 回调和 WEB_URL 用了旧端口（3000/3001）
- **根因**：早期项目端口为 3000/3001，迁移到 7300/7301 后未同步更新
- **修复**：改为 7301（API）和 7300（Web）
- **文件**：`.env`

#### 6. search.controller.ts 鉴权装饰器矛盾
- **现象**：搜索接口同时标注 `@Public()` 和 `@UseGuards(ApiKeyAuthGuard)`，但 `ApiKeyAuthGuard` 内部也检查 `@Public()` 直接放行，导致 ApiKeyAuthGuard 的 scope 检查形同虚设
- **根因**：设计意图是"匿名可搜索，带 API Key 可记录用户"，但实现方式让两个装饰器互相抵消
- **修复**：移除冗余的 `@UseGuards(ApiKeyAuthGuard)`（搜索接口本来就是公开的，scope 检查对匿名用户无意义）
- **文件**：`apps/api/src/modules/search/search.controller.ts`

#### 7. link-checker vote 接口设计不一致
- **现象**：`vote` 接口用 `userId?: string`（可选），但没标 `@Public()`，匿名用户投票会被全局守卫拦截返回 401
- **根因**：设计是"匿名可投票，登录后记录用户"，但忘记加 `@Public()`
- **修复**：添加 `@Public()` 装饰器
- **文件**：`apps/api/src/modules/link-checker/link-checker.controller.ts`

#### 8. agreement.controller.ts create 用 0n 作为 adminId
- **现象**：创建用户协议时 adminId 硬编码为 `0n`，TODO 注释说"从 CurrentUser 获取"
- **根因**：开发时遗留的 TODO 未完成
- **修复**：用 `@CurrentUser('sub')` 获取真实 adminId
- **文件**：`apps/api/src/modules/agreement/agreement.controller.ts`

#### 9. AppHeader 退出后未导航
- **现象**：点击"退出"按钮只调用 `authStore.logout()`，用户仍停留在需登录页面，后续 API 调用全部 401
- **修复**：退出后 `navigateTo('/')` 回首页
- **文件**：`apps/web/components/AppHeader.vue`

#### 10. useApi token 过期检测不可靠
- **现象**：`err.message.includes('Token')` 依赖错误消息字符串匹配，但 `$fetch` 抛的是 `FetchError`，其 `message` 是 HTTP 错误描述，不包含后端返回的 `message` 字段
- **根因**：未区分 HTTP 错误和业务错误
- **修复**：改为检查 `statusCode === 401` 或 `data.code === 20003`，并提取后端 `data.message` 作为错误消息
- **文件**：`apps/web/composables/useApi.ts`

### 次要

#### 11. stop-dev.bat 误杀其他项目进程
- **现象**：原脚本用 `taskkill /F /IM node.exe` 杀所有 node 进程，会误杀其他项目的 node
- **修复**：改为按端口精准定位（7300/7301）杀进程
- **文件**：`stop-dev.bat`

#### 12. start-dev.bat 用 WINDOWTITLE 过滤无效
- **现象**：原脚本 `taskkill /F /IM node.exe /FI "WINDOWTITLE eq SeekAll*"` 过滤条件不生效（node 进程没有窗口标题）
- **修复**：同上，改为按端口过滤
- **文件**：`start-dev.bat`

## 四、预防措施（避免下次同类问题）

### 1. Windows 路径空格问题
**规则**：在 Windows bat/PowerShell 脚本中，所有路径变量必须用引号包裹，启动子进程时优先用 PowerShell `Start-Process -WorkingDirectory` 而非 `cmd /c`。

**检查清单**：
- [ ] 路径变量是否用 `"%VAR%"` 包裹
- [ ] 启动子进程是否指定 `-WorkingDirectory`
- [ ] 重定向日志路径是否含空格且正确引用

### 2. 前后端字段对齐
**规则**：前端 reactive 对象字段必须与后端 DTO 字段一一对齐，新增后端字段时同步更新前端。

**检查清单**：
- [ ] reactive 对象是否包含所有 DTO 字段
- [ ] 提交前 grep 确认字段名拼写一致
- [ ] 后端 DTO 变更时同步检查前端调用

### 3. 鉴权装饰器组合
**规则**：
- `@Public()` 表示接口完全公开，不要与 `@UseGuards()` 同时使用
- 若需"可选鉴权"（匿名可访问，登录后记录用户），只用 `@Public()` + `@CurrentUser() user?`，不要加 `@UseGuards()`
- 若需强制鉴权 + scope 检查，只用 `@UseGuards(ApiKeyAuthGuard)` + `@RequireScopes()`，不要加 `@Public()`

**检查清单**：
- [ ] 接口是否明确公开或鉴权
- [ ] `@Public()` 和 `@UseGuards()` 是否同时出现（不应同时出现）
- [ ] 可选 `userId?` 是否对应 `@Public()`

### 4. 数据库列长度
**规则**：URL 类字段默认 VarChar(2048)（网盘分享链接可能很长），不要用 512。

**检查清单**：
- [ ] URL 字段是否 ≥ 2048
- [ ] 邮箱字段 128，用户名 32，密码哈希 256
- [ ] 长文本用 `@db.Text` 或 `@db.LongText`

### 5. 环境变量配置
**规则**：端口迁移后必须全局搜索旧端口号，确保所有配置文件同步更新。

**检查清单**：
- [ ] `.env`、`.env.example`、`.env.production` 端口一致
- [ ] OAuth 回调 URL 端口正确
- [ ] `nuxt.config.ts` 代理目标端口正确
- [ ] `ecosystem.config.cjs` 端口正确

### 6. 前端错误处理
**规则**：`$fetch` 抛出的 `FetchError` 要检查 `statusCode` 和 `data`，不要依赖 `message` 字符串匹配。

**检查清单**：
- [ ] token 过期检测用 `statusCode === 401`
- [ ] 业务错误用 `data.code` 判断
- [ ] 错误消息优先取 `data.message`

### 7. 进程管理
**规则**：停止服务时按端口精准杀进程，不要 `taskkill /F /IM node.exe` 杀所有 node。

**检查清单**：
- [ ] stop 脚本是否按端口过滤
- [ ] 是否会误杀其他项目进程

## 八、搜索效果优化（追加修复）

### 问题
用户反馈"很难找到用户想要的资源"，搜索"三体"等关键词 0 结果、10s 超时、2 个源失败。

### 根因分析
1. **PanSou API GET 方式不稳定**：偶发 302/400/403/33s 响应，`src=all` 参数触发 Cloudflare 拦截
2. **Provider 超时冲突**：PansouProvider 内部 10s 超时 × 3 次重试 = 30s，远超 ProviderService 全局 10s 超时，第一次请求就被全局超时中断
3. **3 个 Provider 重复调用同一 PanSou API**：pansou/quark/tg-channel 都调 `so.252035.xyz`，重复请求触发限流
4. **0 结果无兜底**：实时搜索 0 结果时直接返回空，没有 fallback 到 Meilisearch 索引
5. **MagnetProvider 被禁用**：`.env` 中 `MAGNET_SITE_URL=` 为空
6. **缓存 TTL 判断错误**：用 `total`（实时结果数）而非 `finalTotal`（含 fallback）判断 TTL，导致 fallback 结果被当 0 结果短缓存

### 修复措施

#### 1. PanSou Provider 改用 POST 方式
- **文件**：`pansou.provider.ts`、`tg-channel.provider.ts`、`quark.provider.ts`
- **变更**：`fetch(url, { method: 'GET' })` → `fetch(url, { method: 'POST', body: JSON.stringify({kw, res, ...}) })`
- **效果**：POST 比 GET 稳定（避免 URL 编码问题和 Cloudflare 拦截），响应时间从 0.7-33s 稳定到 4-5s

#### 2. 优化超时配置
- **PansouProvider/TgChannelProvider**：内部超时 10s → 4s，重试 2 次 → 0 次
- **ProviderService**：全局超时 10s → 12s
- **.env**：`PANSOU_TIMEOUT=4000`、`QUARK_TIMEOUT=4000`、`MAGNET_TIMEOUT=4000`
- **效果**：单次请求 4s 超时，不重试，快速失败后 fallback

#### 3. 0 结果自动 Fallback 到 Meilisearch 索引
- **文件**：`search.service.ts`
- **变更**：实时搜索 0 结果时，自动调用 `fuzzySearch` 从 Meilisearch 索引兜底
- **效果**：即使 PanSou API 返回 0 结果，用户也能看到历史索引中的相关结果

#### 4. 启用 MagnetProvider
- **文件**：`.env`
- **变更**：`MAGNET_SITE_URL=https://bt4gprx.com`
- **说明**：bt4g 在国内被墙，但不影响其他 Provider（各自独立超时）

#### 5. 缓存 TTL 用 finalTotal
- **文件**：`search.service.ts`
- **变更**：`getCacheTtl(req.keyword, total)` → `getCacheTtl(req.keyword, finalTotal)`
- **效果**：fallback 成功的结果用长缓存（10min/1h），避免被当 0 结果短缓存 30s

### 已知限制
1. **PanSou API 数据源不稳定**：某些关键词（如"三体"）PanSou API 返回 0 结果，需依赖 Meilisearch 索引兜底。索引数据来自历史搜索，覆盖度有限。
2. **bt4g 磁力搜索被墙**：国内无法访问 bt4gprx.com，MagnetProvider 实际不可用。需要配置可用的磁力搜索镜像或自建代理。
3. **TG/DHT 索引未建**：等 TG Collector 配置（2026-07-14 上午 10 点用户发 key）和 DHT Crawler 部署后自动建索引。
